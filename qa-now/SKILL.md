# QA Now — 即时需求追问

立即审查当前任务的描述，找出模糊点、隐含假设和未明确的技术决策，并以结构化方式向用户追问。**不做猜测，不做假设，不做未确认的实现。**

## 核心理念

AI 开发中最大的浪费：理解的需求 ≠ 用户设想的。用户脑海里有很多"显然"的东西没说出来，AI 不会读心术。

与其做出不符合预期的产出再返工，不如在动手之前把模糊点全部搞清楚。

## 何时追问

### 你应主动追问的信号（即使在对话中，未调用本 Skill）

碰到以下任一情况，**停下来追问**，不要继续实现：

- 用户说"做一个 X"但没说用什么技术栈、什么框架、什么平台
- 涉及多个可选的方案（如"要不要分页"、"存数据库还是文件"、"同步还是异步"）用户没表态
- 用户对现有代码提修改要求，但没说明期望的具体行为变化
- 用户提到"好看"、"好用"、"快点"、"简单"等主观词但没给标准
- 需求有隐含的前置条件（如"需要用户登录"但在描述中未提认证）
- 涉及数据模型但未定义字段、关系、约束
- 多步骤流程但中间步骤未指定行为
- 边界情况用户明显未考虑（空数据、错误处理、并发冲突）

### 用户主动调用

用户说以下任意一句话时，执行本 Skill：

- `/qa-now`
- "qa-now"
- "帮我审查一下需求有没有遗漏"
- "追问一下"
- "质疑我"
- "clarify"
- "检查需求完整性"
- "你觉得还有什么没说清楚的"
- 或任何表达"帮我审视需求描述是否完整"的表述

## 追问方式

### 追问格式

每轮追问最多列出 **3-5 个核心问题**，按重要性排序。每个问题：

1. **引用模糊原文** — 让用户知道你在针对哪句话提问
2. **指出歧义** — 列出可能的理解方式（2-3 个）
3. **给出推荐** — 如果你有倾向，给出推荐并说明为什么（可选）
4. **收窄回答范围** — 问选择题比问开放式问题效率高

```
🤔 "打造一个管理系统" —— 什么类型的管理？
   A. 用户/权限管理
   B. 内容/文章管理
   C. 商品/订单管理
   D. 其他（请说明）
   → 如果是通用后台，推荐从 B 入门门槛最低。

🤔 "界面好看就行" —— 请给一个参考标准
   A. 只要功能能跑，丑一点无所谓
   B. 参考主流 SaaS（简洁、灰白调）
   C. 有参照物（给我一个你觉得"好看"的网站/截图）
   D. 我自己有 UI 设计稿，后续提供
```

### 追问原则

- **不要为简单问题追问。** 用户说"在 README 加个 badge"——这种不需要追问。
- **不要追问风格偏好。** 除非用户提了，否则自行决定配色/字体/间距。
- **技术决策要追问。** 数据存哪里、什么架构、什么库——这些影响产出方向。
- **每次最多 5 个问题。** 太多了用户会跳过。
- **追问后停止，不要同时实现。** 等用户回答后再继续。
- **如果用户说"随便"/"都可以"，直接做决定并告知选择的方案。**

### 追问同时做的事情

你可以同时输出你对明确部分的 **理解摘要**（3-5 句），让用户知道你已经理解的部分：

```
✅ 我的理解（确认一下）：
- 做一个 Web 应用，前后端分离
- 前端 React，后端用你现有的 FastAPI 模板
- 部署到 Vercel（前端）+ Railway（后端）

🤔 需要确认的：
（追问列表）
```

这样用户既能确认你已经 get 到的部分，也能针对性地回答追问。

## 追问节奏

- **每轮 3-5 个问题**，太多会让人跳过
- **追问后暂停等待**，不要边追边做
- **单一澄清**：一次追问只针对一个用户描述，不要混多个话题
- **收敛到收窄**：第一轮可能问大类，第二轮针对已选大类问细节

## 触发边界

**→ 主动追问（不调用本 Skill 也执行）：**
- 涉及开放式技术决策
- 数据模型、架构方向未指定
- 主观质量标准未量化

**→ 不需追问的：**
- 一句话精确指令（"在 line 42 加一个 console.log"）
- 纯事实查询（"Linux 如何查看端口占用"）
- 明确的代码修复（"这个 button 点击没反应，帮我修"）

## 注意事项

- 别拿「你确认要继续吗」当追问 —— 那没提供任何信息。给具体的分叉选项。
- 用户不耐烦时（"别问了直接做"），立刻停止追问，开始实现并在产出后标注你做的假设。
- 追问不意味着你不理解用户的领域 —— 是你在帮他把他脑海里"显然"的东西外化出来。
