# Make Tutorial

这个 Skill 用来创建**完整的中文教程体系**，以多文件 HTML 站点形式输出。

目标是帮助用户围绕某个主题产出一套**结构清晰、内容充实、易于理解、可直接在浏览器中打开学习**的教程网站。产物应该像一门真正的课程，而不是提纲扩写或模板化拼装。

---

## 核心定位

这个 Skill 应当生成**专业级教学内容**，而非玩具示例或入门速成。

目标是产出：
- **深度足够**：不止讲"是什么"，还讲"为什么"和"怎么用"
- **覆盖完整**：包含核心概念、边界情况、常见陷阱、最佳实践
- **生产就绪**：示例代码可直接用于实际项目，而非演示玩具
- **系统化**：有清晰的知识图谱和递进路径，不是零散知识点堆砌

它支持：
1. **从零新建一套教程**
2. **根据已有文档整理、重写或扩展成教程**

但核心始终围绕：
> **专业级教程体系，能让学习者真正掌握主题并应用到实际工作**

---

## 为什么用 HTML 而不是 Markdown

Markdown 在教学内容呈现上有明显局限：

| 能力 | Markdown | HTML |
|------|----------|------|
| 代码语法高亮 | 依赖渲染器 | 原生支持（Prism.js） |
| 代码一键复制 | 不支持 | 支持 |
| 可折叠章节 | 不支持 | `<details>` |
| 提示框/Callout | 非标准 | 完全可控 |
| 标签页切换 | 不支持 | 可实现 |
| 表格样式 | 极有限 | 完全可控 |
| 内嵌交互示例 | 不支持 | 可实现 |
| 视觉层次控制 | 有限 | CSS 完全控制 |
| 离线可用 | 需渲染器 | 双击即开 |

HTML 教程可以直接在浏览器中打开，无需任何工具链，同时拥有远超 markdown 的表现力。

## 触发后的基本行为

当使用这个 Skill 时：

1. **先理解用户真正想做什么。**
   - 识别教程主题。
   - 判断是从零新建，还是基于已有材料整理。
   - 尽量从当前对话中推断足够信息，而不是机械发问。

2. **不要死板追问。**
   - 如果信息已经足够，就直接开始设计教程。
   - 只有当答案会显著影响课程结构、深度、路线或示例时，才提出补充问题。

3. **不要套固定模板。**
   - 不强制固定章节数。
   - 不强制固定命名方式。
   - 不强制所有主题走同一种教学路线。

4. **按主题本身来长结构。**
   - 不同主题需要不同的章节边界、叙事顺序和重点。
   - 语言教程、框架教程、数学教程、图形学教程、工程教程不应该长得一样。

5. **默认产出真正可学习的教程，而不是轻量提纲。**
   - 每章通常都要有足够展开。
   - 避免只写提纲式内容，除非用户明确要求先出草案。

## 何时提问

只有在这些信息缺失且会显著影响结果时才提问：

- **学习者基础**（零基础 / 有相关经验 / 进阶 / 专家级）
- **学习目的**（入门探索 / 工作应用 / 面试准备 / 项目实战 / 深入研究）
- **技术栈 / 语言 / 框架 / 版本**
- **深度要求**：
  - 快速入门（覆盖基本用法）
  - 系统掌握（覆盖核心概念 + 常见场景 + 最佳实践）
  - 深度专精（覆盖原理、源码、性能优化、生产陷阱）
- **实战要求**：是否需要完整项目、代码审查要点、故障排查指南
- **是否要求独立成体系**
- **是否希望参考已有文档**
- **输出目录与命名偏好**
- **是否要先出目录再确认**

如果从上下文已经能合理判断，就不要为了"流程完整"而发问。

**默认深度：** 如果用户未明确说明，默认按"系统掌握"级别设计（不是入门速成，也不是源码解析）。

## 输出设计原则

### 1. 按主题决定结构
结构必须从主题本身长出来。
不要把所有教程都改写成同一种壳。

### 2. 教程默认独立成体系
除非用户明确要求和已有教程组成课程联动：
- 不要大量引用旧教程当作默认前置
- 不要写成"在前面的 OpenGL 教程里我们已经学过……"这类强依赖
- 可以举跨主题例子，但不要把旧教程变成新教程的必要上下文

### 3. 教程要足够详细，但不能臃肿
目标是：
- **深度足够教学**：不止讲 API 用法，还讲设计思想、适用场景、权衡考量
- **包含实战经验**：常见错误、调试技巧、性能考量、生产环境注意事项
- **示例贴近真实**：不是 `foo/bar` 玩具代码，而是真实场景的简化版
- **有层次不堆砌**：概念 → 用法 → 场景 → 陷阱 → 最佳实践，而非信息倾倒
- **可验证掌握**：每章结尾提供练习题、思考题或实战任务，让学习者检验理解

**避免：**
- 只列 API 不讲为什么这样设计
- 示例代码只能跑通但不能改、不能扩展
- 只讲正常路径，不提边界情况和错误处理
- "这个很简单，大家自己试试"式的甩手

### 4. 保证递进关系
章节之间应该有自然推进关系：
- **基础概念**：核心抽象和设计思想
- **核心机制**：工作原理和关键特性
- **实际用法**：常见场景和代码模式
- **深入理解**：边界情况、性能考量、底层机制
- **生产实践**：错误处理、调试技巧、最佳实践
- **进阶主题**：性能优化、架构设计、源码解读（如果需要）

顺序应该让读者觉得"为什么下一章在这里出现"是合理的。

**专业教程的特征：**
- 不止讲"怎么用"，还讲"什么时候用"和"什么时候不该用"
- 包含真实项目中的权衡和取舍
- 提供故障排查和调试思路
- 引用官方文档、源码或权威资料作为深入学习路径

### 5. 主题专属性必须强
教程应该让人一看就觉得：
> 这是由深度使用过该技术的专家编写的课程

而不是：
> 这是一个通用教程模板，把主题名替换了一下

具体要求：
- **强调该主题真正核心的概念**（不是泛泛而谈的通用编程概念）
- **示例要像这个领域会出现的例子**（真实场景的简化，而非玩具代码）
- **章节划分要符合该主题真实的知识结构**（不是死板的"入门-进阶-高级"三段式）
- **包含该领域的特有陷阱和最佳实践**（不是任何技术都适用的泛泛建议）
- **引用该领域的权威资源**（官方文档、经典书籍、关键论文）
- **提供真实的调试和故障排查经验**（不是"遇到问题就查日志"这种废话）

**检验标准：** 如果把教程中的技术名词全部替换成另一个技术，内容仍然说得通，那就是不合格的通用模板。

## 编写流程

### Phase 1：理解需求并决定方案
- 识别主题、受众、深度要求
- 如果有现有文档，用 `Glob` + `Read` 分析
- **主题风格自动判断**：技术类→tech，数学类→math，科学类→science（用户无需关心，自动选择最合适的）
- 缺关键信息时才提问（默认：系统掌握级别）
- **章节生成**：不论多少章，一张一张生成。生成完一章再生成下一章。

### Phase 2：生成教程文件
1. 先 `Read references/assets.md` 获取 CSS/JS 代码
2. 创建 `assets/` 目录和资源文件
3. 创建 `index.html`（在开头说明主题风格选择理由）
4. 创建各章节 HTML（参考 `Read references/chapter-example.md`）
5. 每个页面都要带主题切换按钮和 `<head>` 内联主题脚本（见下节，默认必做）

**如果 references 文件读取失败**：使用简化的内联 CSS（基础排版+代码高亮），但深/浅色切换不能省。

### Phase 3：完成前验证
用 `Glob` 列出所有 HTML 文件，随机 `Read` 2-3 个章节检查链接和路径，并确认：
- 每个页面都有 `data-theme-toggle` 按钮和头部内联主题脚本
- 组件规则里没有写死的颜色值（`Grep` 搜 `#fff`、`#ffffff`、`background: white` 之类）

交付时说明：
- 使用了哪个主题风格（tech/math/science...）及原因
- 完成了哪些章节
- 主题切换的使用方式：按钮在页面顶部，首次跟随系统，手动选择跨页保持
- 如何修改：直接 `Edit` 对应的 `.html` 文件

## 基于现有文档整理教程

如果用户是要"根据已有文档编写教程"：

1. 先检查已有文件
2. 找出：
   - 内容重叠
   - 顺序不合理
   - 缺少解释
   - 缺少衔接
   - 缺少教学层次
3. 重新组织成学习导向的结构
4. 必要时重写内容，而不是仅仅重命名或重新打包

不要只是把资料堆成一个目录。要把它变成真正能学的课程。

- 所有资源使用相对路径引用

## 深色/浅色主题切换（默认必做）

**每套教程都必须自带深色/浅色切换，不需要用户额外提要求。** 这是默认交付标准，不是可选增强。

硬性要求：

1. **每页都有切换按钮。** `index.html` 和所有章节页都要有 `data-theme-toggle` 的按钮；`script.js` 里已内置"缺失时自动补一个"的兜底，但不要依赖兜底，模板里该写的就写上。
2. **首屏不能闪。** `<head>` 里必须放内联脚本，在绘制前把 `data-theme` 写到 `<html>` 上。放到 `</head>` 之前，不能放 `</body>` 前——那样深色用户会看到一帧白底。
3. **首次跟随系统，之后记住选择。** 无记录时读 `prefers-color-scheme`；手动切换后写入 `localStorage`，键名 `tutorial-theme`，值只有 `light` / `dark`。所有页面共用同一个键，翻页不跳。
4. **颜色全部走令牌。** 组件规则里禁止字面色值（`#fff`、`#333`、`#ddd`、`background: white`），否则切一半就停，出现白底白字或深底深字。新增组件时先在 `style.css` 的 `:root` 和 `[data-theme="dark"]` 里各补一条令牌。
5. **代码块两套主题都保持深色。** Prism 固定 `prism-tomorrow`，背景由 `--bg-code` 控制，不要为深色模式换浅色 Prism 主题。
6. **交付前实测两种模式。** 正文、`h2` 下边框、表格表头、四类提示框、章节徽章、行内代码、代码块、导航链接、切换按钮本身，逐项确认没有低对比区域。

令牌清单、完整 `style.css`、`script.js` 和头部内联脚本的写法见 `references/assets.md`；六个主题各自的深浅两套品牌色见 `references/theme-system.md`。

## HTML 页面模板

每个章节 HTML 文件应遵循以下基本结构：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <meta name="color-scheme" content="light dark">
    <title>章节标题 - 教程名称</title>
    <link rel="stylesheet" href="https://cdnjs.cloudflare.com/ajax/libs/prism/1.29.0/themes/prism-tomorrow.min.css">
    <link rel="stylesheet" href="assets/style.css">
    <link rel="stylesheet" href="assets/theme-tech.css">
    <script>
        (function () {
            try {
                var saved = localStorage.getItem('tutorial-theme');
                var theme = saved || (window.matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light');
                document.documentElement.setAttribute('data-theme', theme);
            } catch (e) {
                document.documentElement.setAttribute('data-theme', 'light');
            }
        })();
    </script>
</head>
<body>
    <nav class="chapter-nav">
        <a href="index.html">目录</a>
        <a href="上一章.html">← 上一章</a>
        <a href="下一章.html">下一章 →</a>
        <button class="theme-toggle" type="button" data-theme-toggle aria-pressed="false">深色</button>
    </nav>

    <main>
        <h1>章节标题</h1>
        <!-- 正文内容 -->
    </main>

    <footer class="chapter-footer">
        <nav class="chapter-nav bottom">
            <a href="上一章.html">← 上一章标题</a>
            <a href="下一章.html">下一章标题 →</a>
        </nav>
    </footer>

    <script src="https://cdnjs.cloudflare.com/ajax/libs/prism/1.29.0/prism.min.js"></script>
    <script src="https://cdnjs.cloudflare.com/ajax/libs/prism/1.29.0/components/prism-python.min.js"></script>
    <script src="assets/script.js"></script>
</body>
</html>
```

`index.html` 没有 `nav.chapter-nav`，把切换按钮放在 `main` 之前的 `.page-toolbar` 里：

```html
<body>
    <div class="page-toolbar">
        <button class="theme-toggle" type="button" data-theme-toggle aria-pressed="false">深色</button>
    </div>
    <main>
        <h1>教程标题</h1>
```

**完整示例**：参考 `references/chapter-example.md` 查看一个专业级章节的完整实现（Python 异常处理）。

**资源文件**：参考 `references/assets.md` 获取完整的 CSS、JS 和主题样式代码。

## 写作风格要求

优先：
- **具体表达**（用真实场景和代码说话，而非抽象概念）
- **渐进讲解**（从简单到复杂，从具体到抽象）
- **建立直觉**（解释"为什么"比罗列"是什么"更重要）
- **例子贴近真实使用**（不是 `foo/bar`，而是实际项目会遇到的场景）
- **解释设计权衡**（为什么这样设计？有什么替代方案？各有什么优缺点？）
- **提供调试思路**（遇到问题怎么排查？常见错误信号是什么？）
- **教程语气自然**（像有经验的工程师在分享，而非文档生成器）

避免：
- 只有 bullet list 的浅层章节
- 大量未解释术语堆砌
- 假设读者知道并未声明的背景
- 填充式废话（"这个很重要"、"大家要注意"这类空话）
- 能原封不动套到别的主题上的空泛内容
- **玩具示例**（`add(1, 2)` 式的无意义演示代码）
- **缺少错误处理的示例**（真实代码必须处理错误）
- **没有使用场景说明的 API 列表**（不是 API 文档的翻译）

利用 HTML 优势适度加入：
- 可折叠的进阶/补充内容
- 多语言对比标签页
- 好/坏写法对照表格
- 带样式的提示框（info / warning / tip / danger）
- 步骤流程图
- **实战代码示例**（可直接运行和修改）
- **故障排查清单**（常见问题 + 解决方案）
- 侧边注释

## 成功标准

一套成功的教程体系应该：
- **看起来像专业课程**，而非入门速成或玩具教程
- **可以直接应用到实际工作**，学完能上手真实项目
- **结构是为该主题量身定制的**，不是套模板
- **深度相对均匀**，后面章节不是敷衍了事
- **足够具体和可学习**，有真实代码、真实场景、真实问题
- **全部使用中文讲解**
- **视觉风格与主题匹配**
- **默认支持深色/浅色切换**：每页都有按钮，首次跟随系统，选择跨页保持，首屏无闪烁
- **颜色全部走 CSS 令牌**，两套主题下正文、表格、提示框、代码块对比度都达标
- **充分利用 HTML 的表现力**（不是 markdown 换了个后缀）
- **双击 index.html 即可开始学习**，无需任何工具链
- **明显不是模板批量导出的产物**
- **包含验证掌握程度的方式**（练习、项目、检查清单）
- **提供深入学习路径**（官方文档、源码、进阶资料）

**专业级教程的标志：**
- 学习者完成后能在面试/工作中自信地使用该技术
- 包含真实项目中会遇到的问题和解决方案
- 不回避复杂性，但用渐进方式讲解
