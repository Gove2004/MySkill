# Godot Procedural Kit

本技能用于在 Godot 中提供**程序化内容实现方案**。

重点不是某一种游戏类型，也不是某个项目模板，而是以下能力：
- 用代码生成可视内容
- 用代码生成交互反馈
- 用代码减少外部资源依赖
- 用可复用结构组织程序化模块

## 适用范围

当用户有以下需求时，应优先使用本技能：
- 希望用 `_draw()`、脚本或运行时节点生成视觉内容
- 希望减少贴图、音频、预制体等资源依赖
- 需要程序化 UI、形状、粒子、音效、地图或视觉反馈
- 需要把一套程序化实现迁移到多个 Godot 项目
- 需要可复制的 Godot addon 或纯脚本方案

当问题主要是以下方向时，不应把本技能当成首选：
- 纯剧情、关卡设计或数值策划讨论
- 与程序化生成无关的 Godot 普通 API 问题
- 与具体库、服务端、平台 SDK 集成有关的问题

## 能力覆盖

本技能主要覆盖以下几类内容：

1. **几何绘制**
   - `_draw()` 图形绘制
   - 几何 UI
   - 基于形状的视觉表达

2. **程序化粒子**
   - 用脚本生成粒子行为
   - 粒子生命周期与表现控制
   - 低资源依赖的反馈实现

3. **程序化音效**
   - 基于 gdfxr 的音效生成
   - 基础音频播放组织
   - 无音频素材场景下的快速接入

4. **程序化地图与结构生成**
   - 网格生成
   - 基础连接与路径结构
   - 可迁移的地图生成思路

5. **程序化视觉反馈**
   - 环形、脉冲、光束、闪烁等通用效果
   - 强调“逻辑行为 + 可见反馈”的同步设计

## 内置插件资源

本技能自带一组可直接复制到项目 `addons/` 目录的资源，位于：
`bundled_addons/`

当前内置：
- `gdfxr/` — 程序化音效生成
- `sound_manager/` — 音频播放管理
- `phantom_camera/` — 相机相关能力

## 插件使用原则

使用内置插件时，遵循以下原则：
- 只复制当前任务需要的插件
- 优先最小接入，不一次性启用全部资源
- 如果纯脚本即可解决，就不要额外增加插件依赖
- 输出方案时要明确哪些内容依赖插件、哪些不依赖插件

## 工作方式

使用本技能时，按下面的顺序组织输出。

### 1. 识别目标

先判断用户要生成的是哪一类内容：
- 界面或绘制内容
- 粒子或反馈内容
- 音效内容
- 地图或结构内容
- 通用程序化模块

### 2. 确认约束

在给出完整方案前，优先确认这些约束：
- 是否允许使用 addon
- 是否要求纯脚本
- 是否允许运行时动态创建节点
- 是否有性能上限或平台限制
- 是否已有现成场景树或基础系统

### 3. 选择实现层级

根据需求选择以下输出形式之一：
- **局部代码片段**：用于回答单点问题
- **完整脚本**：用于提供可直接挂载的模块
- **模块化方案**：用于跨文件组织程序化能力
- **插件接入方案**：用于直接复用 `bundled_addons/`

### 4. 组织答案

每份输出尽量使用下面的结构：

```text
## 模块名
### 作用
### 实现步骤
### 完整代码
### 挂载方式
### 可调参数
### 依赖项
### 注意事项
```

## 通用实现原则

### 1. 优先保持模块独立

程序化模块应尽量做到：
- 输入明确
- 输出明确
- 与具体项目结构弱耦合
- 能独立复制到其他项目中使用

### 2. 区分“生成逻辑”和“展示逻辑”

尽量把：
- 参数计算
- 生命周期管理
- 绘制/播放/显示

拆成可理解的层次，而不是全部堆在一个 `_process()` 或 `_draw()` 里。

### 3. 控制运行时生成成本

如果方案依赖运行时创建节点、频繁 redraw 或全量扫描对象，应主动考虑：
- 更新频率
- 同屏对象数量
- 是否可以缓存引用
- 是否可以减少瞬时峰值

### 4. 反馈要和逻辑同步

程序化反馈不应只是“逻辑完成后的装饰”。
在设计视觉或音频效果时，要让用户能清楚感知：
- 何时开始
- 何时结束
- 何时命中/触发/切换
- 哪个状态正在生效

### 5. 方案要便于参数化

输出代码时，优先把易变内容参数化，例如：
- 颜色
- 尺寸
- 速度
- 生命周期
- 数量
- 间隔
- 透明度
- 强度

## 通用技术注意点

### `_draw()`
- 适合几何表达和轻量视觉内容
- 不会自动替代复杂资源工作流
- 需要注意 redraw 频率
- 需要自行处理布局、缩放和锚点语义

### 运行时节点生成
- 适合临时对象、动态效果和按需构造
- 需要注意初始化顺序
- 需要注意节点路径稳定性
- 需要注意销毁和回收时机

### 粒子与几何多边形
- 形状越复杂，越需要注意尺寸下限和顶点合法性
- 生命周期缩放时应避免非法 polygon 数据
- 同屏数量增长时应优先做预算和节流

### 音频生成
- 适合快速原型、低资源依赖和功能验证
- 不等于最终音频资产方案
- 若使用插件，应明确安装与启用步骤

### 地图生成
- 先明确输出是什么：网格、连通结构、房间、路径还是布局
- 先明确约束是什么：尺寸、连通性、随机性、可重复性
- 算法描述应与具体玩法解耦，优先说明输入、输出和规则

## 常见工程问题

### 1. 初始化顺序问题

如果代码通过 `new()`、`set_script()`、`add_child()` 组织对象，要注意：
- 属性在什么时候赋值
- `_ready()` 在什么时候运行
- 默认值会不会覆盖外部传入值

### 2. 路径依赖问题

如果脚本依赖固定节点路径，要注意：
- 场景树调整后路径是否仍有效
- 是否应改成导出引用、依赖注入或更稳的查找方式

### 3. 重复触发问题

凡是“在某个条件区间内触发一次”的逻辑，都要防止每帧重复执行。
应显式区分：
- 未触发
- 已触发
- 重置条件

### 4. 性能问题

出现卡顿时，优先检查：
- 是否 redraw 过于频繁
- 是否节点数量增长过快
- 是否存在高频全量扫描
- 是否短命对象生成过多
- 是否同一事件被重复触发

### 5. GDScript 类型推断问题

在数组、字典、group 查询和中间变量较多的脚本中，必要时应显式标注类型，以降低推断失败和可读性问题。

## 输出要求

使用本技能时，答案应尽量满足以下要求：
- 给出可直接复制的 Godot 代码
- 明确脚本挂载位置或接入方式
- 标清插件依赖
- 标清可调参数
- 避免把方案绑死到某个具体项目叙事或玩法模板
- 优先提供可迁移、可裁剪、可复用的实现

## 局限

- `_draw()` 方案通常需要手动维护布局、缩放与重绘策略
- 程序化粒子与运行时生成对象更容易遇到性能瓶颈
- 程序化音效适合快速生成与验证，不一定替代最终音频制作流程
- 通用方案只能提供结构和实现模式，具体视觉风格仍需按项目调整
